本文是 `Gaudi-LLM` 项目的**唯一踩坑总台账**（服从 [`../AGENTS.md`](../AGENTS.md) 第五节记坑纪律；现行架构与阶段状态以 [`../ROADMAP.md`](../ROADMAP.md) 为准）。

## 一、TPC 硬件算术、指令集与编译器坑（`P-TPC`）

### `P-TPC-01`：`v_exp_f32` 在分界点处的硬件算术失真 `[已证实]`
- **现象与触发**：单层同输入同专家集合下，Layer 44 Rank 7 的 MoE 门控激活相对 FP64 误差异常飙至 `0.001311`（其余 Rank 贴近 FP64）；单卡掩码 Softmax 在特定负输入处的最大绝对概率误差高达 **`0.166667`**。
- **真实根因**：Gaudi2 TPC 的 `v_exp_f32` 指令在区间约化分界点存在硬件算术缺陷——例如对 `x = -ln(2)` 返回 **`1.0`** 而非 **`0.5`**。凡直接调用裸 `v_exp_f32` 计算 SiLU/Sigmoid 或 Softmax 的算子均受波及。
- **硬性铁律解法**：严禁在算子中裸调单次 `v_exp_f32`；必须采用经边界验证的二次指数分解修正（已在 MoE FP32 Gate、Full-Attention Softmax 与 SWA Softmax 三处实测将单卡最大概率误差压至 `3.39e-6`、Rank 7 MoE 误差压至 `6.41e-5`），并抽成全算子库统一复用的公共安全数学头文件（配 750+ 分界邻域回归单测）。
- **证据落点**：`gaudi-kernels` 公共头 `csrc/tpc/common/tpc_math_safe.h`（提交 `7fd1f90`）及 750 点设备回归 `tests/tpc_safe_exp_boundary.cpp` / `tools/run_tpc_safe_exp_boundary.py`（提交 `502c072`）；750 个边界样本与三种算子单卡数学快筛收据 SHA256：`d10ab28752b4b30be1696087f5b2d841aad5a65b6fa0dec95bf94c883d72ba3d`。三种新旧内核编译 `.text` 和单卡测试的完整输出张量均逐位一致（`max_abs=0.0`），收据 SHA256：`0765f89bfa6f35204d3f41549c641748dd53481f6cc052fc0874530cfaa66d33`。此前收据：`e40cd3a74f785f4d5c5dfd0dd640fefd8b3ad2e6ff076aec18da48686461ba26`、`286c537925034796eeeb6ce159e58f7fa5264f0a5408af6fc97c8a05f9416fd4`。

### `P-TPC-02`：标量 `SLM` 与向量 `VLM` 地址空间物理隔离导致 `-O2` 删加载 `[已证实]`
- **现象与触发**：标量解码后写入本地内存、再用向量加载 `v_f32_ld_l_v_b` 读出时数据恒为 `0.0`；开启 `-O2` 后编译器直接删除上游 packed/scale 向量加载指令。
- **真实根因**：TPC 的标量本地内存（`SLM`）与向量本地内存（`VLM`）是两块物理不通的独立地址空间。往 `SLM` 写再从 `VLM` 读在数据流上无有效消费者，触发编译器合法的死代码消除（DCE），并非编译器“乱丢指令”。
- **硬性铁律解法**：严禁用 `SLM <-> VLM` 往返搬运数据；跨标量/向量路径一律走文档化的谓词寄存器搬运（predicated scalar-to-vector move）或纯向量流水线，并用冲激输入 + `tpc-llvm-objdump` 验证 `LD_G -> MAC` 完整消费链。
- **证据落点**：`instance-assets/single-card/20260923T081629Z/tpc/`、`20260923T083422Z/tpc/`。

### `P-TPC-03`：启用 LUT / SFU 后可用 `VLM` 容量腰斩至 `16 KiB` `[已证实]`
- **现象与触发**：编译参数带 `-vlm 32` 可正常编过，但上真机运行 `24 KiB` activation tile 时直接触发设备侧异常或主机侧内存报错崩溃。
- **真实根因**：TPC 硬件在启用特殊函数单元（SFU）/ 查表（LUT）模式时，会将硬件表空间切走一半 `VLM`，实际可用 `VLM` 上限降为 **`16 KiB`**。
- **硬性铁律解法**：凡使用 SFU/LUT 的 TPC 内核一律按 **`<= 16 KiB`**（`-vlm 16`）硬约束规划本地向量工作集，禁止假设 32 KiB 常驻可用。
- **证据落点**：`instance-assets/kernel-overheads-20260927/`。

### `P-TPC-04`：同一 VLIW 指令包内两个大立即数互相覆盖编码 `[已证实]`
- **现象与触发**：汇编/编译零报错，但运行期循环步长错乱（如 `add I5, 128` 实际执行效果变成 `+32768`）。
- **真实根因**：Gaudi2 VLIW 指令包（bundle）的共享立即数槽位有限，同一拍内塞入两个大立即数时编码位域发生覆盖。
- **硬性铁律解法**：循环步长与大偏移常量在循环外预装入标量寄存器，手写或关键内联汇编改动后必须用 `tpc-llvm-objdump --triple=tpc --mcpu=gaudi2` 核对反汇编字面值。
- **证据落点**：`instance-assets/kernel-first-principles-20260927/`。

### `P-TPC-05`：`-O2` 将冷分支 `if-convert` 成主路径谓词指令 `[已证实]`
- **现象与触发**：在循环内写极低概率触发的边界兜底分支（fallback），结果正常路径稳态 VPU/SPU 指令数与耗时显著上升。
- **真实根因**：TPC `-O2` 默认对分支做 `if-conversion`（无 `jmpr` 硬件跳转跳过），冷分支被转为带谓词指令每拍照常发射，白占 VPU 槽位。
- **硬性铁律解法**：热循环内部禁塞分支兜底；将整块主循环与尾块（tail）在循环外显式拆成两段无分支流水。
- **证据落点**：`instance-assets/kernel-overheads-20260927/`。

### `P-TPC-06`：MXFP4 裸 `DATA_PACKED_MXFP4` 不做硬件译码，nibble 解包需两步对齐 `[已证实]`
- **现象与触发**：直接用 typed tensor descriptor 加载 `DATA_PACKED_MXFP4` 读出的仍是原始打包字节；仅做 `UNPCK_4_TO_8` 时 512 个有序码出现奇偶通道错位。
- **真实根因**：`DATA_PACKED_MXFP4` 仅为主机侧张量标记，硬件加载管线不自动做 E2M1/E8M0 浮点反量化；load-pipe `4->8` 解包后必须配合 `convert.u4 all_lanes` 才能对齐奇偶 nibble 通道，F32->BF16 双半交织置换需在离线打包阶段逆向吸收。
- **硬性铁律解法**：按 `U8` 原始字节加载，遵循 `UNPCK_4_TO_8 -> convert.u4` 或经全 512 码对拍的成对 256-entry LUT 译码；权重静态置换一律在离线/加载期吸收，不留给在线解码核。
- **证据落点**：`docs/mxfp4-verdict.md`、`instance-assets/mimo-layer1-20261026/moe-loader-equivalence-v1/`。

### `P-TPC-07`：LUT 基址与函数 ID 错配踩零地址，及 `LOOKUP_AND_MAC` 语义误读 `[已证实]`
- **现象与触发**：使用 LUT 时触发设备访问地址 `0` 错误；或误把 `LOOKUP_AND_MAC` 当向量点积使用。
- **真实根因**：`set_lut_32` 配 32-entry 基址却调用 256-entry 函数 ID 会越界踩零；256-entry 成对表须配 `set_lut_256`（base `0xCD8/0xCDC`，表项为连续 16-bit halfword）；而 `LOOKUP_AND_MAC` 硬件语义是分段二次多项式 `C0 + x*(C1 + C2*x)`，并非线性点积。
- **硬性铁律解法**：使用 256-entry LUT 前必须先跑满全 256 键单测验证基址与函数 ID 配对；不臆猜未验证 intrinsic 名字语义。
- **证据落点**：`instance-assets/kernel-first-principles-20260927/`。

### `P-TPC-08`：`shuffle` 仅限自身 16-word 组内且 `bit7` 为通道使能位 `[已证实]`
- **现象与触发**：调用 `v_u8_shuffle_b` / `u32 shuffle` 输出全零，或跨组收集（gather）数据错乱。
- **真实根因**：控制向量方向字节的 **`bit7` 是输出使能位**（`bit7=0` 且 `income=0` 时直接填零），且硬件映射范围严格限制在各自的 **16-word 组内**，不支持跨组任意重排。
- **硬性铁律解法**：组内重排必须置位 `bit7`；跨组重排改走 `unpack + convert` 或双输入置换指令，上线前跑全通道冲激映射单测。
- **证据落点**：`instance-assets/kernel-first-principles-20260927/`。

### `P-TPC-09`：Index-Space 合并 Tile 漏遍历 `get_index_space_size()` `[已证实]`
- **现象与触发**：输出张量预填哨兵值（sentinel）后，跑完内核发现大量输出行仍保留哨兵未更新。
- **真实根因**：图编译器可能合并相邻逻辑 tile，`get_index_space_offset()` 只是当前核分到区间的起点，单次调用的跨度由 `get_index_space_size()` 给出；且逻辑 128 tiles 不自动保证跑满全部 24 个物理 TPC 核。
- **硬性铁律解法**：内核外层必须完整循环遍历 `[offset, offset + size)`；单测输出缓冲区必须预填非零/NaN 哨兵校验全覆盖，并用活跃核计数确认 24 核负载均衡。
- **证据落点**：`MANIFEST.md`、`instance-assets/kernel-coverage-20260926/`。

### `P-TPC-10`：TPC 反汇编与手册工具链误导 `[已证实]`
- **现象与触发**：普通 GNU `objdump` 把 TPC ELF 反汇编成乱码 x86 助记符；临时 `_slots.o` 报 `<unknown>`；`man tpc-clang` 声称 `-march` 只支持 `dali`（初代 Goya）。
- **真实根因**：`habanalabs-tools` 随包 man 手册严重过期；反汇编必须走专用 LLVM 后端并显式指定 Gaudi2 目标与含 `.tpc_metadata` 的对象文件。
- **硬性铁律解法**：编译固定传 `-mcpu=gaudi2 -O2`，反汇编固定用 `tpc-llvm-objdump --triple=tpc --mcpu=gaudi2`，内建函数原型一律以 `tpc-clang -E` 实提的 `tpc-defs.h` / `tpc-special.h` 为准。
- **证据落点**：[`../MANIFEST.md`](../MANIFEST.md) 第 3–4 节。

### `P-TPC-11`：静态 VPU 指令条数大幅下降但真机墙钟几乎不动 `[已证实]`
- **现象与触发**：静态反汇编显示 VPU 指令减少 53%，真机算子耗时仅降 8%。
- **真实根因**：小 `M` 解码核多受限于 LSU 访存延迟、长依赖链 stall 或核心数未打满，静态指令数不等于运行期关键路径周期。
- **硬性铁律解法**：禁止拿反汇编指令行数报喜；唯一裁判是真机同形状设备事件与端到端墙钟。
- **证据落点**：`instance-assets/kernel-overheads-20260927/`。

### `P-TPC-12`：大桶 SWA 对逐行页表全表扫描 `[单卡与整模单跑已验证]`
- **现象与触发**：M512 的单层 SWA 图在真实权重和冻结输入下 p50 为 `6.451 ms`；整模诊断中 SWA、Dense 和 Embedding 的合并流区间占比最大。
- **真实根因**：图构造器为每行连续存放两个窗口页表项，但通用批量内核为每行搜索全部 `2 × M` 个条目，重复进行标量读取。该扫描随桶大小平方增长；整模区间还包含其他算子，不能把全部耗时归因于扫描。
- **硬性铁律解法**：对已声明的逐行两项契约使用专用内核，按 `2 × row` 直接读取；入口校验页表形状，保留通用内核供其他布局使用。M512 和 M32 在真实权重、相同输入下分别与逐行 M1 对拍，输出与 KV 逐位一致。
- **证据落点**：M512 单卡基线日志 SHA256：`c1df48609c808e47b87043546dc2cabad1dee1bc08c7600ac973ddf4f4b78feb`；直接索引版本 p50 `2.725 ms`、逐位对拍日志 SHA256：`0161b29d418e8542ccce4621c205ef205f573e2851c56855a1182dd26680bf69`。局部结果不能乘以层数当整模成绩。无插桩服务单跑 p50 从 `7622.05 ms` 到 `5846.05 ms`，对应收据 SHA256 分别为 `4cfe4e14db6f2ecd08912f506bb5670fdf0f6233817ea5e7484a46c9401542b3`、`71c785d461c9b9cc0caf35e663b53f5d6d06507649dfeaa7f9d835cfc87a059b`；这是两次单跑，未经 ABBA 排除漂移。

### `P-TPC-13`：当前 TPC 编译器拒绝 `unsigned long long` `[编译期已证实]`
- **现象与触发**：为一般浮点 `arange` 探索设备端宽整数求值时，以 `-mcpu=gaudi2` 编译含 `unsigned long long` 参数及算术的最小 TPC 核，前端直接报该类型不受支持。
- **真实根因**：当前 TPC C/C++ 编译器 `2.7.33` 的目标类型检查拒绝该声明；该结果本身不能证明硬件或 Synapse 的 INT64 算子不可用。
- **硬性规避**：不要在 TPC C 核中直接依赖此 C 类型；若需要宽精度计算，须使用已验证的设备算子或明确实现并逐位验证多字运算，不能因此把设备张量静默退回 CPU。
- **证据落点**：仓外最小源码 SHA256 `68eedb0602658b90ebc494a0c6abc52380fd5063f4f09d25c42462d01c9850b7`、编译诊断 SHA256 `a74746941c3bda17e347741b0a113ea209483f75e8227b782350400a8cbe4c8d`；该探针未执行真机数值计算。

## 二、量化格式、浮点舍入与数值对拍坑（`P-NUM`）

### `P-NUM-01`：Gaudi2 硬件 FP8 `E4M3` 为 IEEE-Specials，与 Checkpoint `OCP-FN` 同名不同义 `[已证实]`
- **现象与触发**：对 OCP `float8_e4m3fn` 权重直接调设备侧原生类型转换时，顶带数值（`0x78..0x7e` / `0xf8..0xfe`）直接炸出 `Inf` / `NaN`。
- **真实根因**：Gaudi2 硬件 FP8 E4M3 遵循 IEEE 特殊值编码（指数全 1 含多个非有限码，有限饱和顶码为 `0x77 / 0xf7`），而主流训练产出的 OCP `e4m3fn` 仅 `0x7f / 0xff` 为 NaN、其余皆为合法有限大数。
- **硬性铁律解法**：权重加载期（CPU/离线）必须按全 256 码表显式完成 OCP-FN 到硬件安全表示的解码/映射；在线激活若进原生 FP8 MME 必须先卡安全幅值带，严禁在解码热循环里为避坑塞通用查表慢分支。
- **证据落点**：[`mxfp4-verdict.md`](mxfp4-verdict.md)、`gaudi-kernels/python/gaudi_kernels/block_fp8.py`。

### `P-NUM-02`：MXFP4 `E8M0` `byte0 = 2^-127` 与 32 元素分组边界 `[已证实]`
- **现象与触发**：小幅值输入出现精确 50% 相对误差；或均匀 scale 测试全过、换成真实非均匀 scale 后每隔 16/32 列成片算错。
- **真实根因**：OCP MX `E8M0` 无符号指数定义为 `2^(b - 127)`，故 `byte = 0` 是 `2^-127`（FP32 位型 `0x00400000`）而非 `2^-128`；且每 **32 个 K 元素**（16 个打包字节）共享 1 个 `E8M0` 字节。用全常数 scale 做单测会完全掩盖分组步长错位。
- **硬性铁律解法**：单测必须包含非均匀奇偶跳变 scale 与 `x = 2^120` 放大探针（隔离 subnormal 冲零干扰），全 256 个 `E8M0` 码值逐一校验。
- **证据落点**：[`mxfp4-verdict.md`](mxfp4-verdict.md)、`instance-assets/p2-mxfp4-salvage-20260923/`。

### `P-NUM-03`：设备 FP32 Subnormal 整结果归零（Flush-to-Zero）`[已证实]`
- **现象与触发**：当完整浮点结果落入 FP32 非正规数区间（`< 2^-126`）时，CPU FP32/FP64 参考为非零极小值，Gaudi2 设备输出精确为 `0.0`。
- **真实根因**：硬件执行单元对非正规结果做 Flush-to-Zero。
- **硬性铁律解法**：仅允许对“整个数学输出本身处于 FP32 subnormal 区间”的样本做具名豁免；严禁借此放宽正常量级输出的误差阈值。
- **证据落点**：[`mxfp4-verdict.md`](mxfp4-verdict.md)。

### `P-NUM-04`：PyTorch CPU `FP64 -> BF16` 经 `FP32` 中转的双重舍入假阳性 `[已证实]`
- **现象与触发**：拿 PyTorch CPU `tensor_fp64.to(torch.bfloat16)` 当“黄金真值”对拍时，某个距离 BF16 中点 `1.28e-8` 的 QKV 样本与设备输出差 1 ULP，误判为设备算错。
- **真实根因**：当前环境下 PyTorch 的 `float64 -> bfloat16` 先舍入到 `binary32` 再舍入到 `bfloat16`（Double Rounding），在临界中点处会选到与 IEEE 直接 `binary64 -> BF16` 最近偶数舍入相反的邻居，而设备选的才是直接舍入正确值。
- **硬性铁律解法**：构建高精度 CPU 参考流时，从 `FP64` 落 `BF16` 层间契约必须使用 IEEE 直接位级最近偶数舍入函数，禁止直接调 `.to(torch.bfloat16)` 充当裁判。
- **证据落点**：`GaudiRT` `docs/mimo-numeric-correction.md`；收据 SHA256：`d30f789b4b234dc19c281c472196775da1b5d3db08e833b9ab7efe3`。

### `P-NUM-05`：融合 RMSNorm 残差提前舍入 BF16 与 SWA Value 缩放精度丢失 `[已证实]`
- **现象与触发**：早期融合 `grid24` Norm 把 `hidden + residual` 先舍入成 BF16 再算均方根，以及 SWA Value 写入前用 BF16 做缩放，导致写入 KV 的相对误差升至 `0.00157 ~ 0.00387`，70 层累积后首步 KL 恶化。
- **真实根因**：Transformer 数学契约与 GPU FlashInfer 标杆一致要求残差相加后的归一化方差归约及 Value scaling 在 FP32 寄存器内完成后再落 BF16 存储。
- **硬性铁律解法**：层边界残差存储为 BF16，但算子内部 `residual_add + RMSNorm` 累加与 QKV Value 缩放一律保持 FP32 计算后再写回 BF16 KV。
- **证据落点**：收据 SHA256：`1a53142c52377f3eb54f12452cfbb7c78f7ba43e1dff8700f8e9a3996611e2d1`、`350e5e4306c15215aec7961a937dbb707b2dcb57f1d482a0781a675de2a59c1c`。

### `P-NUM-07`：MoE 重复专家 ID 坍缩与 `0 * Inf/NaN` 掩码污染 `[已证实]`
- **现象与触发**：随机路由单测含同行重复专家 ID 时，官方 MoE 算子误差飙到 `60%+`；或对未命中槽位做 `* 0.0` 掩码、对全掩码注意力块做 `max` 减法时炸出 `NaN`。

- **证据落点**：[`mxfp4-verdict.md`](mxfp4-verdict.md) 第 3.3 节。

### `P-NUM-09`：QKV 归约落在 BF16 中点时丢失残差造成二次舍入 `[已证实，修复限模型契约]`

### `P-NUM-18`：FP32 到 INT32 的正溢出转换与 CPU 结果不一致 `[单卡局部验证]`
- **现象与触发**：使用官方 `cast_f32_to_i32` 和向零舍入，在 FP32 输入 `2^31`、`2^40` 时设备输出 `2147483647`，当前 PyTorch CPU 参考输出 `-2147483648`；普通范围样本通过并不能覆盖该差异。

### `P-NUM-19`：INT64 到 FP32 的大数转换存在舍入差异 `[单卡局部验证]`

### `P-NUM-20`：INT32 到 BF16 在中点附近的 PyTorch 存储语义 `[单卡局部验证]`

### `P-NUM-21`：跨 INT32 边界的整数序列中间乘加可能静默算错 `[单卡局部验证]`
- **现象与触发**：从 `-2147483648` 到 `2147483647`、步长 `2147483647` 的设备序列，使用 INT32 索引乘加时最后一项为 `-2147483648`，CPU 结果为 `2147483646`。

- **证据落点**：CPU 标量边界探针 SHA256 `e0675b63ba7b2f012a0a6a516f9c644a021c4857f3a4e40b4475c5520abee9fc`。`GaudiRT` `f78d4a8` 的 6 种长度冷暖设备回归最大行相对 FP64 误差 `1.03e-7`、CPU FP32 最大底噪 `0.004193`，暖载 12 张、重编 0 张，输出逐字节一致；冷、暖记录 SHA256 `c1ea17f514472f4bafefb57718da45555de55989bd2986056beca4f0063a65d8`、`dd998f6369fa71bc9c4e6a616beeb7da760cb51ef66b832732faec5f8153ad60`。仅覆盖所记录的标量和形状。

### `P-NUM-32`：QKV 投影的少量舍入翻转可放大为整层超差 `[多重补算已撤回；新整层数值待验证]`
- **现象与触发**：两层合成模型的非空在线前缀逐层对拍中，第 0 层行相对 L2 为 `0.0035805`，超过当时样本门限 `0.0031723`；同一单层空前缀样本此前通过。仅在两种 MME 归约的 BF16 结果不一致时补算后，另一三层样本仍以 `0.003803845 > 0.003` 失败。这些旧参考在层内含 BF16 舍入，结果不能替代现行纯 FP32/FP64 层参考的验证。
- **真实根因**：冻结相同输入时，两层样本的归一化对直接舍入 FP64 逐位一致，QKV 的 `9216` 个 BF16 结果中有 6 个不同；捕获的 MME FP32 值确认部分值跨越 BF16 中点。三层失败样本中，两种 MME 归约虽得到相同 BF16，仍与直接 FP64 的 QKV 结果不同；普通 FP32 横向归约亦可能丢失决定中点方向的低位。冻结候选 Q/K/V 后的单层重放支持投影舍入差异经后续计算放大；这些证据不证明闭源 MME 的内部归约顺序。
- **硬性规避**：撤回以多次 GEMM、整表切分和逐元素补算迎合 BF16 中点的做法；线性层使用一次原生 MME，严格保留真实存储边界。不得因此降低第四节数值门槛，必须以同输入、同在线 KV 前缀的整层结果对独立 FP64 和同边界 CPU FP32 验收。上述已失败冻结样本须在新注意力路径完成后重测，不能由孤立投影通过推定整层通过。
- **证据落点**：旧两层逐层失败 SHA256 `99635bac86cdc2b069dae11d790f7379501baa61db29557901095e5ed20c3b1e`；归一化与 QKV 隔离 `74d6222c8a7d53360eb61d89b0f79b9f5da148666696736ccb3d51ab9bf436f9`；旧补算实现的真实权重 52 层收据 `b913a80c50c4e4a722a99aa3949bcecfa0bca62b5a5c2755124dc4411369f907` 的参考在层内多次舍入 BF16，仅作旧口径诊断，不能证明符合当前整层纯 FP32 底噪门槛。`GaudiRT` `f78d4a8` 与算子包 `6d735f1` 删除补算后，目标宽度 `7168` 的两层投影及拆分在 `M=1/7/137` 最大行相对 L2 为 `0.000379147`、FP32 最大底噪 `0.000367940`，冷暖逐字节一致、暖重编 0；记录 SHA256 `2c9ea49b618189c394ffbfa2db94b23da2bbac6692fbe3bf0ec515bd5b2d9274`、`3368dc088b90d7a99df7408dc8161e532594bc7fd8304ef1fbb6c2a5b373f0ff`。这不证明新整层或整模已达标。

### `P-NUM-33`：完整层纯 FP32 底噪与孤立注意力的 BF16-PV 对照不可混用 `[新分块设备路径待验证]`
- **现象与触发**：旧单次 BF16 概率乘法的 `56:8/128` 孤立单行样本在 63 和 4096 位置相对 FP64 误差为 `0.00325632`、`0.00923166`；曾按完整层的 `0.003` 门槛判孤立算子失败。第四节现明确孤立算子的两个独立阈值，旧样本未计算同分块 BF16-PV 误差，尚不能判定通过。此前又把 BF16 概率混入纯 FP32 底噪并报告通过，该结论仍撤回。
- **真实根因**：将候选内部 BF16 量化塞进 `CPU_FP32_same_boundary` 会人为抬高完整层参考底噪。独立 CPU 模拟在 4096 位置、块大小 256 的样本中，相对 FP64 误差为 `0.00641167`，说明单次 BF16 分块概率乘法在该输入存在舍入误差；这不是设备性能或所有输入的上界。
- **硬性规避**：完整 Decoder 层含 `o_proj + residual`，其 FP32 参考内部保持纯 FP32，层输出继续严格执行 `max(3e-3, 2 * err(CPU_FP32, CPU_FP64))` 及 `0.01` 上限；整模 KL 门槛不变。孤立无残差注意力另须同时满足相对独立 FP64 `<= 1e-2`、相对同分块 BF16-PV 参考 `<= 1e-3`，该 BF16-PV 参考不得用于完整层底噪；禁止为迎合孤立样本增加第二次 `P@V`。
- **原生节点补充**：独立 Synapse `sdpa_recomp_fwd_bf16` 非因果探针中，5D 广播的 `M=3/KV=5/QH=4/KVH=2/D=64` 输出相对 FP64 的最大整行误差为 `0.00354421`，相对单块 `BF16(exp(scores - tile_max)) @ BF16(V)` 参考为 `0.00389775 > 0.001`；同一样本恰好与先归一化再转 BF16 的诊断参考一致。闭源节点内部步骤和其他几何不由该结果证明，且该节点并未验证分页 KV、在线分块或端到端性能，不能直接接入。探针记录 SHA256 `488198cd34f030dbfff0d563430a0b4220651e934bc196ccc74f95f52a8c8c9f`。
- **证据落点**：旧设备样本 SHA256 `7ebaf851441cc5dae2d99591b49095463b5cfed979e628b7e5bc0d0b669d6c4b`、`c1d203d45f4f372127866d1c4524dc769fd7dd4f6d186ef5005b7799259f849b`；独立 CPU 分块模拟记录 `59b2c13d93a87f619d641dd4c6c1c87bb6494c595b9368b24ed362cc44911a7f`。`GaudiRT` `caab0ca` 和算子包 `2349389` 撤回误加的 BF16 底噪舍入；`GaudiRT` `c6dd889`、`d36c71b` 分别测试孤立双门槛与已覆盖的纯 FP32/FP64 冻结层参考，CPU 回归 SHA256 `d9da916508fe2a8e152ac1ffb080c3c3660ef626d8f89402543382afcc259040`、`62f84344f80e752aff2d86cd9bc980a4f2efd38b8c4b399b28e4a6b4bd3b64d7`。错误参考记录 `b2b2a3eca36b0b8e73a15b9ee06ead550881b281ceae9bb51dbcb04c9b0e7fc2` 不用于验收；新设备与全层结果待测。

## 三、Synapse 图编译、运行时与生命周期坑（`P-RT`）

### `P-RT-01`：自定义 TPC `.so` 缺入口符号或漏配官方 `libtpc_kernels.so` 兜底 `[已证实]`
- **现象与触发**：`synNodeCreate` 报 `No Entry point GetShapeInference`；或只把 `GC_KERNEL_PATH` 设成自研 `.so` 后连基础算子都报 `GlueCode 400`。
- **真实根因**：Synapse Kernel DB 要求自定义算子库完整导出 `GetKernelGuids`、`InstantiateTpcKernel`、`GetShapeInference`、`GetSupportedDataLayout`、`GetLibVersion` 五个 C 符号；裸装环境默认未设 `GC_KERNEL_PATH`，覆盖时仍需保留官方库在冒号列表末尾提供通用算子。
- **硬性铁律解法**：构建期用 `nm -D` 强校五符号齐全；运行期固定设置 `GC_KERNEL_PATH=<ours_1.so>:...:/usr/lib/habanalabs/libtpc_kernels.so`。
- **证据落点**：[`redeploy.md`](redeploy.md) 第 4 节。

### `P-RT-02`：Persistent Section 混绑与运行期动态按名查表 `[已证实]`
- **现象与触发**：图编译报 `checkInputPersistence` / launch section mismatch，或每步发射在主机侧反复按字符串查找张量 ID 浪费 CPU 时间。
- **真实根因**：外部可读写张量未各自绑定独立 persistent section、混用 `synTensorSetHostPtr` 与 section 地址修补，或在解码热循环里重复调元数据查询。
- **硬性铁律解法**：每个外部动态/权重张量分配独立 persistent section；编译/加载期一次性通过 `synTensorRetrieveIds` 固化整数 `tensorId` 静态绑定数组，解码步只改地址槽位直接发射。
- **证据落点**：`GaudiRT` `src/recipe_registry.cpp`。

### `P-RT-03`：“声明放 SRAM”被编译器刷回 HBM 及 RMW `16 MiB` 限制 `[已证实]`
- **现象与触发**：构图时给中间张量设了 SRAM 提示，结果性能没涨甚至在两轮 ABBA 中方向反转。
- **真实根因**：`synGraphCompile` 后置调度 Pass 可能根据容量/切片决策插入 DMA 落回 HBM，且单个 RMW Section 存在 `16 MiB` 容量限制；盲目强开 RMW 或跨算子大合图可能导致编译器排程倒退。
- **硬性铁律解法**：绝不把“代码里写了放 SRAM”当成物理驻留证据；一切 SRAM 驻留与合图粒度改动必须通过单变量 ABBA 实测净收益裁决，负收益或不稳定立即撤回（如已撤回的 Layer 1 RMW 实验）。
- **证据落点**：[`../ROADMAP.md`](../ROADMAP.md) 第三节、`GaudiRT` `docs/software-autopsy.md`。

### `P-RT-04`：`synLaunch` 外壳 CPU 开销与设备重叠错觉 `[已证实]`
- **现象与触发**：底层 `scal_stream_submit` 写硬件队列仅 `0.38 µs`，但 `synLaunchWithExternalEventsExt` 单次耗时 `22 ~ 33 µs`（含每次堆分配 `RecipeLauncher`、重复校验与关不掉的内部环形日志原子锁）；反过来，单独优化某段主机 CPU 耗时后，整模 TPOT 未必等额下降。
- **真实根因**：当设备计算/通信耗时大于主机下发耗时时，主机 `launch` 与设备执行在流水线上高度重叠——省掉被掩盖的主机 CPU 时间不会直接缩短设备关键路径；但当每步切碎成近 300 次微型算子与集合通信往返（如 70 层 × 2 次 `hcclAllGather`）时，跨图/跨流同步气泡就会暴露成真瓶颈。
- **硬性铁律解法**：不拿“主机 API 耗时降了多少倍”邀功，先用设备事件拆清“算子计算 vs 集合通信 vs 跨图同步气泡”，再决定合图还是动底层队列。
- **证据落点**：[`gaudi2-hardware-vs-software-autopsy.md`](gaudi2-hardware-vs-software-autopsy.md)、`GaudiRT` `docs/software-autopsy.md`。

### `P-RT-05`：公开 Synapse 发射路径的在途信用上限（`<= 575`）`[已证实]`
- **现象与触发**：无节制异步连续塞入大量不同 Recipe 发射而不回收事件时，触发 `MappedMemMgr` 资源耗尽阻塞或失败。
- **真实根因**：公开路径映射内存槽位有限，合成负载实测受 `2 * N_distinct_recipes + N_in_flight <= 575` 约束。
- **硬性铁律解法**：由 `InFlightCreditManager` 管理在途发射信用并按步/按窗口回收完成事件，同构层强制复用同一 `synRecipeHandle`（把 70 层压缩为约 10 张去重 Recipe）。
- **证据落点**：`GaudiRT` `include/gaudirt/runtime/inflight_credit_manager.hpp`、`docs/DESIGN.md`。

### `P-RT-06`：退出阶段原生终止与设备生命周期 `[现象已证实，根因待核实]`
- **现象与触发**：128 步解码与结果落盘全部正确完成，但进程退出阶段 Rank 0 偶发打印原生终止信息甚至以退出码 `1` / `134` 异常终止（如首轮未修退出的 ABBA `B2`）。
- **真实根因**：尚未确定。Python 局部作用域或 `torch._dynamo` 缓存仍持有设备张量、或其他 Rank 尚未完成通信，均是需要验证的生命周期假设；仅凭调整清理顺序后运行成功不能证明具体触发链。
- **硬性铁律解法**：多卡进程退出前必须先过跨 Rank 完成栅栏、同步全部设备流、显式释放编译图与设备张量引用，最后销毁 `DeviceRuntime`；该顺序必须封装进正式 Runner / C++ 生命周期管理，并将**退出码 `== 0` 且零原生终止告警**列为硬验收门禁。
- **补充失败路径**：8 Rank 冻结检查在 L48 抛异常后未执行显式关闭，多 Rank 报原生堆终止，另有两个本次诊断进程滞留；按进程归属清理后八卡释放。这说明诊断异常路径也须执行上述退出协议，具体堆终止根因尚未核实；失败收据 SHA256 `c472de496fda3c9d6b6fbc874f5aa1295401cc46d80e5fe7f18c92fe5a586242`。
- **Phase 5A 单卡补充**：先前锁页池耗尽后未显式清理，以 `134` 原生终止，具体根因仍未核实（失败日志 SHA256 `5e38a5005dc13d941117633b18a89f39f57c89b2c7621f7d77512fd5cb183732`；仅测试作用域清理的日志 `23ef7f9d691ebda7e7d45977f299afc95a0e0fead671420fd19013e6416e6098`）。另一可复现情形是进程正常结束时仍持有设备和锁页张量，退出码为 `255`；栈显示 C++ 静态析构触发 `PinnedHostPool` 的 `synHostFree`，在 Synapse 的缓冲分配器路径段错误，内部失效细节尚未定位（退出日志 `78f6cc88147dd49b3d04ae1dc17af0e9ea992c8f81e2de61d923ff3a8eff6c39`，调用栈 `8b42b6f90ea43b7b5738ac602cc63f65572551dfb1b9f403c77f79af3db653e9`）。通用后端现于解释器退出钩子同步流、归还存活存储的分配租约并销毁运行时；之后对已关闭设备的新操作立即报错。存活张量的正常退出为 `0`，注入异常为预期的 `1` 且无原生终止；收据 `748e747d6d0b8ad5a91d7a1bc2a40ecf7b963d3a7a15161bdf9d145115b4dccf`，退出后各卡恢复基线占用，记录 `af4b2725ccee4d1e777ce756d923cc85744d44f5391df1ec034d175cae519875`。这不证明多 Rank 服务异常路径已完成验证。
- **证据落点**：`GaudiRT` 提交 `21b69b9` 的 `models/mimo/runner.py`、`models/mimo/private_use1.cpp` 与 `tests/private_use1_lifecycle_smoke.py`；四轮 8 Rank、延迟一 Rank 的空权重冒烟通过（CPU 编译图及 `PrivateUse1` 张量，非真实整模），收据 SHA256：`4f3f48a4641529fbd4e5b70be9e944bc4df93e16895f01f696b9be147c159181`。此前运行收据：`175f6c06c7bbd7f1bb404c431fbe6ed346579480be139f861c45ed48517b4b03`、`93c16cb993b1ff0c4f8242e1e70914045c19b1518c01c921e2bc9be0f270a5aa`，不单独证明崩溃根因。

### `P-RT-07`：`.recipe` 磁盘缓存未绑定编译器与算子库指纹导致脏读 `[已证实]`
- **现象与触发**：修改了 TPC 内核 `.so` 或构图 C++ 代码后复用旧磁盘 `.recipe` 缓存，静默跑出旧算子结果。
- **真实根因**：离线序列化的 `.recipe` 内嵌了编译时刻的 TPC ELF 二进制与图结构，不随外部 `.so` 更新而自动失效。
- **硬性铁律解法**：缓存目录路径必须包含构图扩展二进制、`libSynapse.so`、`libSynapseMme.so` 及 `GC_KERNEL_PATH` 全部算子库文件的 SHA256 组合摘要；不匹配直接走冷编或报错。严禁为此手搓 HMAC 签名或 `0400` 权限封条等“安全剧场”。
- **证据落点**：`GaudiRT` `models/mimo/private_use1.cpp`（提交 `febf823`）、[`../AGENTS.md`](../AGENTS.md) 三.7。

### `P-RT-08`：HCCL 默认端口 `12345` 冲突与单机 Scale-Up 驱动边界 `[已证实]`
- **现象与触发**：分布式初始化莫名卡死/握手失败；或裸机 `modprobe habanalabs_ib` 报未知符号。
- **真实根因**：旧桥导入 HCCL 时默认抢占 `12345` 端口（常与本机监控 agent 冲突）；单机 8 卡内部 24×100GbE Scale-Up 互联由 `habanalabs_cn` / `habanalabs_en` 驱动承载，无需加载依赖外部 IB 栈的 `habanalabs_ib`。
- **硬性铁律解法**：零旧桥 `GaudiRT` 直接通过显式 `hcclGetUniqueId` 交换通信句柄，不走默认端口猜测；单机环境不装 `habanalabs_ib`。
- **证据落点**：[`redeploy.md`](redeploy.md) 第 3–4 节。

### `P-RT-09`：PyTorch 与插件入口自动加载已安装的旧桥 `[已证实]`
- **现象与触发**：在未配置隔离变量的 CPU 离线评测进程中，导入 PyTorch 时自动尝试加载 `habana_frameworks.torch`；此外 `vllm_gaudi` 默认插件入口（`vllm_gaudi/platform.py` 第 7 行与 `patches.py`）顶层无条件导入 `habana_frameworks.torch`。
- **真实根因**：当前环境的 PyTorch 设备后端入口点包含已安装的旧桥自动加载器，导入 PyTorch 本身即可触发它；同时旧版 `vllm_gaudi.register()` 直接拉入旧 `HpuPlatform`。
- **硬性铁律解法**：候选主进程、Worker 子进程与离线评测入口均必须在导入 PyTorch 前设置 `TORCH_DEVICE_BACKEND_AUTOLOAD=0`；`vLLM` 零旧桥服务模式在插件入口按配置直接返回独立的零旧桥 Platform / Worker 类，严禁导入旧 `HpuPlatform` 或 `patches.py`，并在初始化期强校 `sys.modules` 与 `/proc/self/maps` 零旧桥映射。
- **证据落点**：`GaudiRT` `models/mimo/runner.py`、`vllm_gaudi/platform.py`；离线现象与隔离验证收据 SHA256：`7020be912798a121c8adc8526dfdb7f793f44cf0192a1a66657c65dd27c943e1`。

### `P-RT-10`：旧模型路径的 `PrivateUse1` 不支持设备张量 `narrow` `[旧路径已证实；通用路径局部修复]`
- **现象与触发**：旧模型路径对设备张量调用 `narrow(...).cpu()`，八卡小张量冒烟均抛出 `aten::as_strided` 未实现异常。通用 `gaudirt` 路径的已测视图及非连续拷贝通过，不能把旧路径问题继续写成通用路径的现行状态。
- **真实根因**：旧模型路径没有注册 `as_strided`，其 `RankContext::address_of` 也拒绝非连续视图；PyTorch 的 `narrow` 依赖元数据视图。该现象与设备数据数值错误无关。

- **硬性铁律解法**：分组 MoE 的内部名称携带层类型与静态桶尺寸；快筛按正式加载顺序覆盖三类图共存。失败进程只按归属清理，确认八卡释放，失败不计入性能。
- **证据落点**：服务失败日志 SHA256：`a879126ed70e1474cc45c758610f65d3ca510b0a13be8ac46c292fd4b571ed69`；8 Rank 三层快筛日志 SHA256：`d8e2a96191778c937410ca2c7522991f806a6fcc4e2be5cd9c98de80e670f1a3`。该记录不代表整模数值或性能通过。

### `P-RT-24`：Prefill 末尾不应为整桶构建独立 TP8 归约 `[单卡对拍通过]`
- **现象与触发**：70 层加载后构建 M512 的独立 TP8 归约图时，`synGraphCompile` 失败，图输入每 Rank 包含 3145728 个 FP32 元素，运行未进入 Prefill。

### `P-RT-25`：`hl-smi` 占用不能单独证明 Synapse 可分配 HBM 耗尽 `[局部实测]`
- **现象与触发**：78 GiB Arena 的 8 Rank 进程运行时，`hl-smi` 显示每卡 `98304 / 98304 MiB`，但三类单层图编译及 HCCL 初始化后，每个进程的 `synDeviceGetMemoryInfo` 均报告约 `15.87 GiB` 可分配。

### `P-RT-26`：客户端收到 token 时 Worker 可能已经执行下一步 `[Worker 内整模审计通过]`
- **现象与触发**：两次 Prefill 后，在客户端收到第二次首 token 时检查全物理 KV，发现第 0 层 Key 的页 33、槽 0 已改变；该页对应首个 Decode 槽位。以客户端输出时刻当作设备步骤边界，无法判断这一变化是否越界。
- **真实根因**：`LLMEngine.step()` 从独立 EngineCore 获取输出，而 EngineCore 自己循环调度；取回某步输出并不阻止 Worker 开始下一步。此外，开始新请求时运行时会清零上一请求的页，跨请求快照必须计入这一明确操作。
- **硬性铁律解法**：非计时 KV 审计在 Worker 完成当前 Prefill 或 Decode 后、返回调度器前检查物理槽位；逐次保留快照，按真实页映射核对写入，并验证其他槽位逐位不变。性能验收不得启用该插桩。
- **证据落点**：含页号、层号和新旧页表的诊断日志 SHA256：`20e2779eddd3f60139d75f5ef0f0f28247efc5278d7d7bac850690ce33d44775`；Worker 内 8 Rank、128 步全物理 KV 审计未触碰区逐位不变，收据 SHA256：`b46c61c8dd654937531ecf396d88a63c1b74dc487afe44599157d82f426719de`。该审计带插桩，不是性能成绩。

### `P-RT-27`：批量 SWA 的页集合不能假定只有两页 `[局部验证]`
- **现象与触发**：128 个连续查询各自的窗口最多跨两页，但整个查询块从 32-token 对齐位置开始时，所有查询窗口的并集可能跨三页；首块还会缺少前一页。
- **真实根因**：窗口随查询位置移动；第一页取块首查询的窗口起点，最后一页取块末查询的位置，不能只复用块首的两个页号。逻辑页和物理页也可能重排。
- **硬性铁律解法**：按块首与块末行的元数据取三页并集，按每行真实位置执行 128-token 因果掩码；缺页输出零。对空 KV、非页对齐和物理页重排做逐位页表核查，再验证完整算子与未触碰 KV。
- **证据落点**：8 个起始位置的设备 Gather 与 CPU 页表逐位对拍日志 SHA256：`ae9d05afaf00d4465ae0a69ffd6c1d5631c966b66a4ed059fa9256155a825c6b`；8 Rank 真实权重局部对拍日志 SHA256：`4bce35295b2442e5bd9ac1c01e31ca3bef7448dea08858d7dab1b603c2f88e80`。该记录不代表整模数值或性能验收通过。

### `P-RT-28`：扩展链接命令包含静态库不等于 Ninja 跟踪静态库 `[本地复现并修正]`
- **现象与触发**：重新编译模型静态库后，扩展目录运行 Ninja 返回 `no work to do`，原扩展的 SHA256 保持不变；强制重链接后扩展 SHA256 改变。
- **真实根因**：生成规则把静态库路径仅放进 `ldflags`，没有把这些库列入链接目标的输入；Ninja 因而看不到静态库的更新。
- **硬性铁律解法**：把所有参与链接的静态库列为链接目标的隐式依赖，或使用全新构建目录；不得只依赖链接命令里出现库路径。构建后检查源码、库和扩展的身份。
- **证据落点**：未重链接日志 SHA256：`0b6799a74849c2ac1ef9dfba4363a4cb623de9f0fa51b3febd61a8bdd1356571`；补隐式依赖后改动静态库触发重链接的日志 SHA256：`e319155ca5a20576d4409308a7e0cf9cca39f9025d019e6a59951b35e4bc9623`。这些是构建验证，不是性能成绩。
- **同步源码保留旧时间戳的另一种失配**：即使 Ninja 已正确跟踪静态库，跨机归档恢复的 C++ 源码若比旧目标文件更早，也可能被判定为无需重编，导致 Python 与扩展不匹配。同步后须使用新构建目录或刷新被替换源码的时间戳，并核对实际编译与链接；不能只看命令返回码。失败记录 SHA256 `7f0f67fc38237f7e8b004b7f33e8a8b2792e45925eac94b7ae753cd668025f57`，刷新后重编及冷暖检查 `f9421a91bc2a8b3b69b85e7247aa3ca7a3c72d5c08d37c6299e369edc93e4e21`。

### `P-RT-29`：增加 Prefill 桶后固定 Arena 可先于物理 HBM 耗尽 `[冷跑通过，暖跑待验证]`
- **现象与触发**：增加 M1024 图和逐层残差缓冲后，78 GiB Arena 的整模初始化在模型权重装载阶段报空间不足；失败进程的退出状态未全部捕获，设备随后已释放。

### `P-RT-30`：大桶单层实验与正式算子包的形状契约可能不一致 `[局部修复验证]`

### `P-RT-31`：不同静态图的同名临时张量可能触发编译形状冲突 `[局部修复验证]`

### `P-RT-34`：单请求 Full Attention 页组不能直接扩成并发页表 `[70 层数值与状态已审计，B8 严格预热待确认]`

### `P-RT-48`：SGLang 采样前的标量减法可经过 CPU 零维包装 `[单卡冷路径验证]`

### `P-RT-49`：SGLang 非重叠调度仍通过 FutureMap 按索引中继 token `[单卡冷路径验证]`

### `P-RT-50`：SGLang 引擎直接关闭会跳过 Worker 退出审计 `[单调度单解码 Worker 验证]`
- **现象与触发**：小几何真实 SGLang 模型生成结束后，主进程退出码为 0，但原有 `Engine.shutdown()` 强杀子进程，不能由此证明 Worker 的旧桥检查或设备清理已执行。

### `P-RT-51`：Prefill 与 Decode 的 Python 模式守卫触发第二次捕图 `[小模型单次捕图验证]`

### `P-RT-52`：仅标记 token 维动态不能保证特征宽度静态 `[特征切片局部验证]`
- **现象与触发**：特征维切片和拼接图在首轮捕图时被编译器拒绝，尽管只显式标记了最外 token 维。

### `P-RT-53`：动态维标记不会消除输入 stride 守卫 `[三维矩阵乘局部验证]`
- **现象与触发**：同一动态 `bmm` 先后接收连续张量和非连续切片时，Dynamo 再次捕图，即使 C++ 配方键相同且没有重复编译 Recipe；单行切片即使被判为连续，也可能触发相同问题。
- **真实根因**：Dynamo 同时守卫输入的实际 stride；动态 token 维标记只覆盖形状，不会使连续和跨步布局共享捕图。PyTorch 在大小为 1 的维度容许不同 stride，故仅检查 `is_contiguous()` 不够。
- **硬性规避**：在捕图入口由 C++ 对非连续动态输入使用流内 D2D 暂存，逻辑形状保持实际 token 数；连续张量的非标准单元素维 stride 用零拷贝视图规范化。桶大小和暂存均由 C++ 决定；跨流使用的暂存别名须登记使用流，整数索引尾部须清零。
- **证据落点**：非连续及单行 stride 守卫诊断 SHA256 `e977feb4223ce98163d2b876e3fb7034ea1ed816d1f5bc55075fe50918200db2`、`8a5d595fc15eb316113deecd738cada0786d84d82d780d7131fb6736aa2e9e9a`；`GaudiRT` `20041a3` / `ea8cd8e` 的生命周期与零拷贝视图，以及 `0cc52f4` 的三维 `bmm/matmul` 冷暖和边界检查，记录 `f9421a91bc2a8b3b69b85e7247aa3ca7a3c72d5c08d37c6299e369edc93e4e21`。SGLang 小模型回归记录 `69ba1e4a84cec18d786433aa23e62279a1a969328e65b405cdd37048ce1bbb7f` 不包含单行 stride 补丁；上述结果只覆盖所测形状。

### `P-RT-54`：暂存别名延长设备运行时寿命会破坏进程退出 `[单卡生命周期验证]`
- **现象与触发**：Python 退出时仍持有图输入暂存别名，退出审计执行后进程异常终止；手工先删除别名则不触发。

### `P-RT-55`：请求批次合并与过滤会改变冷暖常驻图数 `[两层合成模型定位]`
- **现象与触发**：同一两层合成 SGLang 负载的完整 logits 和 KV 冷暖逐位相等、暖进程重编为 0，但末次前向计数分别为冷 67 张、暖 59 张。

### `P-RT-56`：暂存输入后直接返回会丢失原张量别名 `[单卡视图验证]`
- **现象与触发**：编译函数直接返回非连续输入时，返回值数值正确，但设备地址和 stride 对应暂存块而非原输入；仅做数值对拍无法发现。
- **真实根因**：捕图前以连续暂存替换了输入，而返回路径没有把仍指向暂存的别名映射回原存储。初次修复的递归局部闭包又因自引用暂存登记，导致显式关闭时图池仍有存活块。
- **硬性规避**：返回边界检测暂存别名并在 C++ 按原输入布局重建可表示的零拷贝视图；无法保持原布局时直接报错，不能返回副本冒充别名。递归遍历不得自持暂存张量；显式关闭和进程退出分别验证。
- **证据落点**：别名失败 SHA256 `de63784c9feb2908cff6ecc5dae8f980b091304694429347977556a408a6b451`，局部闭包保活失败 `5d6d939b8ce8304b3799431831962359e94c70e31ca21aad5640ab5017f7796c`；`GaudiRT` `bfa2c6a` 覆盖原输入、重复返回、等步长展平、转置及不可表示视图，生命周期记录 `7a5ec6557da4aa3a8b7d3dc24ca44e8afc030220e3b00041229b14387dcb24ab`，原有 Attention 与小模型回归 `fae1bf61dc3bb820df93713ff9abce8458c6acb1c775d94c3e7c0e09d1a198ec`。

### `P-RT-57`：FX 必须区分视图和需要复制的 `reshape` `[单卡视图验证]`
- **现象与触发**：编译图直接返回特征切片或 `split` 结果时，输出数值正确但不共享输入或中间结果的存储；旧测试还错误地要求拆分输出必须连续。三维特征转置后展平时，PyTorch `reshape` 应生成副本，错误地强制视图则会报 stride 不兼容。

### `P-RT-58`：SGLang 的静态显存比例包含已加载权重 `[两层实际权重验证]`

### `P-RT-59`：每批读取设备校验状态会阻塞异步发射 `[单卡局部验证]`

### `P-RT-60`：Dynamo 捕图期间修改 CPU 线程数触发守卫失败 `[两层合成模型验证]`

### `P-RT-61`：合并空闲块时旧事件被反复保留 `[受控单元与单卡跨流已验证]`

### `P-RT-64`：释放缓存块时按在途栅栏高水位扩容造成驱动事件风暴 `[局部修复]`

### `P-RT-67`：动态 TPC 输出的整池序列化覆盖未写入 KV 槽位 `[未解决，危险路径已撤出]`
- **现象与触发**：`2048` 槽、宽度 `1024`、桶 `256` 的 KV 写入实验，`valid_rows=1` 时目标槽写对，但其余 `2,096,128` 个槽位元素被覆盖为零。显式指定输出与对应输入必须复用后，`2048/8192` 槽冷暖运行的目标和其他槽位均正确、暖重编为零，但编译后图仍对两个完整池进行反序列化及序列化。相同核的静态输出版本能保留未触碰区域。把两个相邻小池各声明为 `131072` 槽静态持久段时，发射因持久段地址范围重叠被驱动拒绝；反过来把每个输出描述符缩为 1 槽，试写实际池内的第 `2047` 槽时，目标槽的 `1024` 个元素均未写入，其他槽位未改变。
- **真实根因**：已导出的编译后图明确显示，动态池输入前有 `deserialize_dma`，TPC 写入的是中间张量，随后 `serialize_dma` 将整个动态输出复制到外部池；部分写入的中间输出不能代表此前池内其他槽位。直接使用同一张量作输入和输出则被编译器判为图环。缩小静态描述符时，目标坐标超出声明范围；[TPC 编程模型](https://docs.habana.ai/en/latest/TPC/TPC_User_Guide/TPC_Programming_Model.html)规定张量越界写入由内存控制单元裁剪，与本次未写入现象一致。上述动态输出及段重叠现象均限实测配置，不推断其他形状或配置的行为。
- **硬性规避**：不得把不保留未写槽位的动态输出接入 KV 状态路径；显式输入复用虽修正了所测状态，却不能消除整池搬运，也不符合分块注意力性能要求。固定描述符必须保证其声明的整个范围位于已分配设备内存、同图其他持久段不与其重叠；逻辑槽索引仍须在入口检查，不能依靠较大的描述符发现逻辑越界。所测固定描述符可跳过无效尾行并在写后读取，但尚无整模分配布局和完整分块注意力验证。当前注意力入口继续直接报未实现。
- **证据落点**：动态池逐槽失败 SHA256 `3a80464390c8b736c32ad4ab1a9d951e9830574279ae202bc99db5b04720fb25`；编译后图 `53e5faa637549e653408e5c7c03eb2083dc18eba5a04a83c63c798f629e60d51`；绑定输入复用的冷、暖结果 `4d4eef558a47022a4742521f576e4308fd3c1483128540237ecfa24215d7d384`、`c374437fd9439cc31ffb69733343c3aa1dcda071bcf0f9baf48e5c31cfb83fb6`，对应编译后图 `2229de52ab3aa59cbe56d2697b2d876ea01c4751b3a7571b081e74f66da368f0`；静态输出通过 `198ea263f2969b156ac46b2dd541980c246b52310a3afa02aa74ae7d9b1bc5e8`；大描述符的发射失败 `3e14ad5a18168e89483ce2e1ebe91f663e84bce03ff87e52df43d34242f540ae`，段重叠记录 `ec45850d86b4c8835ddd063c081e1f9921b910a4ad06c53264664a163b81c36d`；单槽描述符越界写入失败 `eca346249614c97c7f9b2a9ce65f8fbdcf9597abbba34ed4ae94ef3ea183b7ff`。`GaudiRT` `0c4d16f` 将两个声明为 `131072` 槽的固定描述符放在同一已分配大块内、并与其他图持久段保持不重叠；实际 `2048/8192` 槽独立冷暖进程中，写入后 Gather 结果、整个逻辑池、桶尾故意越界行及间隔内哨兵正确，暖载 1 张、重编 0，记录 `c0ea62b19baadf50123f4b9f233463e5513c1e4591e5b9bf96ea7adb08a41e88`、`f4e347aa52391951cb379b311c3320b4dc3c6b42e05d558378ea118af00e0280`；另一个同结构图的编译后结果没有动态序列化节点，SHA256 `ba33310f6c979a0fa8a07203f2612951426fa4755e23424a8235777506652e35`。此结果依赖额外间隔和受控索引，不代表 52 层池布局、设备耗时或完整注意力已过关。


### `P-RT-68`：直接绑定的索引视图仍会让静态桶读取逻辑尾部 `[单卡局部修复]`
- **现象与触发**：`M=3` 的连续索引视图由 4 个槽位的对齐存储承载，第 4 个槽位是另一个合法 ID。旧 embedding 图将有效的前三行算对，却把第 4 行也作为桶内索引读取，导致尾行来自该 ID 而非零索引；实际尾值越界时可能产生非法访问。输入本身没有发生修改，因此只检查前三行会漏掉这一问题。
- **真实根因**：对齐、连续和容量充足只证明输入可直接绑定，不证明逻辑 `[M, bucket)` 的内容为零。静态 Gather 的设备描述符看到的是桶尺寸，而不是 PyTorch 逻辑行数。
- **硬性规避**：在 C++ 构图内将已通过入口验证的索引与有效行数送入遮蔽核，遮蔽后的索引再进入 Gather；不得改写外部输入，也不要求 Python 填充。上下文首次使用时建立 `1 MiB` 的 256 字节对齐行数表并完成一次同步上传，之后暖发射只直接绑定对应常量地址，无逐步元数据拷贝。RoPE 与其他消费索引的原语仍须各自验证其 `valid_rows` 截断，不能从本项外推。
- **证据落点**：`GaudiRT` `8e06bb7`；修复前后记录 SHA256 `b96d146e572a9d2c6010728010bd650ab9422372b229306f13091353c8549aee`、`20fac5afccf25e72aae456165c4ffd755b87a1c7b5ffd3fb0a78c0563fa3bd26`。四条流覆盖 `M=3/4/5/7`，另测 `M=1/4095/4096`；同桶复用、输入不变、对齐输入零 D2D、暖发射事件零创建/销毁及退出后重建均通过；embedding 原有样本冷暖输出逐字节一致，暖载 14 张、重编 0，记录 SHA256 `0f7bed0d07cd91fc798ca018053eaef1519ad632141449e67d8ba01e0a85e0e8`、`f75fe78a4a5ba8530b6de4d0b80a5b845267f09e87dd67bd73a8ff7ab3bf5812`。


### `P-RT-69`：缺少退出审计的单次原生失败不能算生命周期通过 `[根因待查]`
- **现象与触发**：一份早期标记为 `split` 的单卡实验状态文件记录退出码 `139`，标准日志为空，进程隔离文件只有入口记录，没有退出记录；同类后续设备图与生命周期测试正常退出。
- **真实根因**：现有记录没有调用栈或更细的运行阶段，无法确定失败发生于计算还是退出，也不能将其归因于旧桥、分配器或某项已修复代码。后续测试通过不证明该次失败的根因已解决。
- **硬性规避**：必须分别保存进程退出码、入口及退出隔离审计，并在复现时采集调用栈；缺失退出记录的运行不得计作生命周期或物理隔离门禁通过。
- **证据落点**：状态文件 SHA256 `690e07064753123c967bbac0180f32da6a753a5bd8b79a47644cef58e776d9f0`、入口记录 `e83dbe81c6f31414d8575a4d6451e947a2a9b40984767e71ed8d59c8f737263b`；本轮归档审计中 294 个进程有干净的入口和退出记录，另 1 个只有入口、无已记录的旧桥映射，汇总 SHA256 `0db650384d8efd62cf1267e5bef81828c675229e6b72b81cf325c623bb6d8313`。进程退出码须另核，汇总不代表 294 项测试都通过。

### `P-RT-70`：单独通过的 KV 与分块算术合图仍触发设备页故障 `[根因待查]`
- **现象与触发**：将固定描述符 KV 写入、设备 Gather、两块 MME 注意力与在线归约放入同一张小几何图后，首次发射期间 TPC 写响应报错，驱动记录虚拟地址 `0` 的页故障并发起设备复位流程；实验进程退出码为 `137`，未产生有效结果。事后监控显示设备占用回到原有 `768 MiB`，但尚未验证设备后续计算。
- **真实根因**：日志证实了页故障、设备写响应和复位流程；具体出错节点、绑定或编译器变换尚未定位，不能把单独通过的 KV 写后读取与未分页算术测试外推为合图安全，也不能认定某一个算子已经查明根因。
- **硬性规避**：当前注意力入口继续在 KV 写入前报未实现；禁止重放该组合图或将它接入模型，先离线检查绑定、索引、张量布局与编译后图并建立可隔离的定位方案。不得手工复位共享设备或把占用回落当成计算验收。
- **证据落点**：进程日志 SHA256 `724a3e048ae4a99bdd93df08a74cd3db6cb2b65bef18edf8c4046dcff343e8b1`、退出状态 `e3b9c2844b5a5c2677b3a2279db2ec8487491dd9a23d6b22fac153391b3bb63c`、驱动记录 `980f3816dadb98f98ab7fe73e61824019dd50bfe5b52351ec027086b8b85be35`、故障分析 `062b99e5056b7eca57fbc5b07b4f3fa53dd7fe8f50f0f5da917a1fec4bdcbdd5`、最终图 `c5e58581bc21b79d5c1a0a7632848fa1c5f1779819427c9ab4f8d7bc5986c321`。

## 四、性能测量与评测防骗坑（`P-BENCH`）

### `P-BENCH-01`：跨层共享 Recipe 导致 Profiler 单层耗时虚高近 60 倍 `[已证实]`
- **现象与触发**：Profiler 抓包里看到名为 `model/N` 的 Recipe 耗时高达 **`2,384.5 µs`**，误以为某一层慢得离谱。
- **真实根因**：同构层复用同一 `synRecipeHandle` 时，`model/N` 只是编译期静态图名而非运行期层号；实测层尾共享 Recipe 每步重复发射 60 次、跨层边界 Recipe 重复 59 次，`2,384.5 µs` 是 **59～60 层累积聚合时间**，不是单层耗时。
- **硬性铁律解法**：严禁引用跨层聚合 trace 数字充当单层基线；单层对照必须在独立同输入 standalone harness 下关闭 Profiler 实测。
- **证据落点**：[`../ROADMAP.md`](../ROADMAP.md) 第三节、`instance-assets/mimo-layer1-20261026/recipe-attribution-v1/attribution.json`。

### `P-BENCH-02`：未消费输出被编译器裁除制造虚假高带宽 `[已证实]`
- **现象与触发**：微基准测出 `5.936 TB/s` 远超物理峰值 `2.45 TB/s` 的荒谬带宽。
- **真实根因**：未被下游消费者读取的输出、重复拷贝或同源随机种子被图编译器 DCE / CSE 静默消除，实际并未执行全部访存。
- **硬性铁律解法**：所有基准测试的输出张量必须被下游消费并在计时外做全量数值校验；高于硬件物理屋脊线的成绩一律先按假阳性排查（真实独立种子实测为 `2.761 TB/s` SRAM）。
- **证据落点**：[`../AGENTS.md`](../AGENTS.md) 一.4。

### `P-BENCH-03`：带插桩/Profiler 耗时当成绩及重叠 Span 直接相加 `[已证实]`
- **现象与触发**：挂着 hook 或 HLTV profiler 跑出的耗时比真实无插桩慢数倍，或把多个并行/嵌套区间耗时直接相加得出大于总墙钟的假账单。单 Rank 事件插桩的 Decode 集合通信区间达到 `27.4 ms`，甚至超过无插桩整步；八 Rank 对称插桩后，同一收据中层内通信分项 `2.954789 ms` 反而大于包含该分项的通信总计 `2.875714 ms`，违反诊断程序的累加关系。
- **真实根因**：插桩改变同步与发射节奏，且 MME、TPC、DMA 与主机提交在时间轴上高度重叠；此外设备原始时间戳约为 50MHz 计数器而非核心主频周期。上述单 Rank 结果存在额外事件创建和 Rank 间等待；对称插桩收据的累加异常具体原因尚未单独证实，不能归咎于硬件。
- **硬性铁律解法**：带 trace / 逐步 KV 审计的运行仅用于定性与定位，**测速必须 100% 关闭插桩**；收益预算只认关键路径墙钟缩减量。必须核对分项与合计的关系，不满足时将该计时标记无效；不能用它推断通信耗时或设备发射间隙。
- **证据落点**：[`../AGENTS.md`](../AGENTS.md) 二.4、`GaudiRT` `docs/software-autopsy.md`；单 Rank 和八 Rank 对称插桩失败样本收据 SHA256：`20969eb7115d3dd460efeffe7e8d79b41ae8e25b9da3077671fcc549408ea695`、`b7d00da8e62f937d41450ea75945f12b18630ce89e21db0577b27e0ef8efb844`。

### `P-BENCH-04`：计时起止口径与主机 CPU 策略不对称 `[已证实]`
- **现象与触发**：同一模型仅因主机 CPU 调频/绑核策略不同，TPOT 从 `11.31 ms` 漂到 `13.37 ms`（差 `18%`）；或候选只计纯设备发射、漏掉客户端输出解码（约 `0.15 ~ 0.35 ms`）乃至调度/IPC 开销，造成不对等胜出。
- **真实根因**：单步 `~10 ms` 级解码对主机线程唤醒、NUMA 亲和及前端处理极其敏感。
- **硬性铁律解法**：ABBA 四臂必须锁定同一主机 CPU 亲和策略与清晰对称的起止边界；若候选尚未接入完整 `vLLM` 调度与 IPC（如 Phase 3 独立解码器），必须在收据与文档中如实标注 `same_complete_production_serving_path_proven = false`，严禁冒充完整线上服务成绩。
- **证据落点**：收据 SHA256：`3a1588c0e449fa8df2f3bacc2d860dced6de624322890e7c2308ed77df80d218`。

### `P-BENCH-05`：评测脚本 `NaN` 比较放行漏洞（Fail-Open）`[已证实]`
- **现象与触发**：算子输出含 `NaN` / `Inf`，但判定脚本写 `if err > tol: fail()`，因 IEEE 中 `NaN > tol` 为 `False` 而以退出码 `0` 假通过。
- **真实根因**：负向不等式判断对 `NaN` 天然漏网，且 Python `json.dumps` 默认可能写出非标准 `NaN` 或崩溃。
- **硬性铁律解法**：所有数值门禁必须前置 `torch.isfinite(out).all()`，并采用正向断言 `assert finite and err <= tol`，失败强制非零退出。
- **证据落点**：[`../ROADMAP.md`](../ROADMAP.md) 第四节。

### `P-BENCH-06`：设备初始化覆盖 vLLM 的 NUMA 亲和与调度策略 `[已证实]`
- **现象与触发**：候选 70 层冷启动使用生产 `vllm_kwargs(diagnostics=False)` 后，Worker 主线程仍分别被固定到 CPU 0、4、8、12、16、20、24、28；部分 Rank 不在 vLLM 选定的 NUMA CPU 集合内，Worker 的 `uclamp.min` 为 1024 而 EngineCore 为 0。
- **真实根因**：`PrivateProgram` 初始化 `DeviceRuntime` 时自行设置 `rank × 4` 的 CPU 和默认利用率夹紧，覆盖了 Worker 继承的生产放置策略；之后创建的线程也可能继承该差异。
- **硬性铁律解法**：服务 Worker 的设备初始化必须原样继承 vLLM 的 CPU 和调度策略；验证各 Rank 及相关线程的实际亲和和夹紧值。修复并实测前，此候选结果不得用于同口径 ABBA。
- **证据落点**：冷启动时 `/proc` 与生产放置配置观察收据 SHA256：`7d62e1acda6b6b38e16ca6d437cf2254ec6dcf083e005ae31f63078daab6f9b2`；`GaudiRT` `66cd1a6` 修复后，8 Rank 主线程亲和均与 vLLM 放置一致，检查到的线程均在对应 NUMA 集合内且 `uclamp.min=0`，全部进程退出码为 0、8 卡释放，轻量日志 SHA256：`18981ff868b52e7f71a0427fbbea21f9c078aad2bffb65d11b4b0c8c08271ec9`。两次均为非计时运行，不是性能结论。

### `P-BENCH-07`：生产对照保留的加载诊断与停用回调容易混入终验 `[单流已核验]`
- **现象与触发**：生产对照加载 70 层权重时逐层打印打包耗时，MoE 路径还保留条件化的边界诊断调用；即使诊断会话未启用，也不能将该运行笼统描述为完全移除诊断。
- **真实根因**：加载计时和诊断条件判断与生产模型实现共处一份 Python 源码；仅清除 Profiler 环境变量并不会删除这些代码。
- **硬性铁律解法**：终验前检查实际执行的生产入口。在仓外隔离副本中只移除加载诊断及关闭状态下的边界诊断分支，保留生产图选择、权重转换、调度和数学路径；不得把带诊断的预检计入正式四臂。生产框架的未预热警告如无逐请求时间标记，应保留其可能影响计时的边界。
- **证据落点**：隔离副本差异 SHA256 `4a3322f42df62351398b73a4a76e245890221c2c676ee6d7aebec9d06b243b5b`；原生产预检与移除诊断后的 A1 三次输出 token 逐位一致，正式单流四臂汇总 SHA256 `5a3bf406eaef9f7b25b5514d514aaca31b51aa63f1eaa724e37e4ccf4478a87e`。该同输出检查不证明所有输入上的等价。

### `P-BENCH-08`：连续批次预热可能漏掉排空阶段的单请求图 `[Batch=8 生产 A1 已核验]`
- **现象与触发**：一次包含 16 条请求的连续 Batch=8 预热后，生产对照的首个正式请求仍出现 8 条单请求 Decode 配置未预热警告；该样本因此不能作为充分预热的终验成绩。
- **真实根因**：预热时的请求到达与排空次序没有覆盖正式运行中出现的 `('decode', 1, 1, 1)` 图配置；不能假定请求总数和最大并发相同就覆盖所有动态批次形状。
- **硬性铁律解法**：在同一组预热请求内先让一条请求走到首次 Decode，再填满并发并完成动态补位；正式请求的到达规则及计时边界保持不变。事后按日志时间戳和请求时间区间核查，正式区间出现未预热警告时不得宣称充分预热。
- **证据落点**：原生产预检警告审计 SHA256 `764b4f7c68330e7bbf755e29ab189d1a51f4500accf41514df8db64dcbc157b3`；调整预热后生产 A1 的 88 条警告均在预热区间，三个正式区间为零，收据 SHA256 `be1f83479b9dd61942fcacc924b21ef8c1434664392837e3e40608c91b376114`。A2 另有 8 条 `('decode', 1, 1, 8)` 警告落在预热结束和首个正式请求开始的同一秒，日志粒度不足以判断归属，收据 SHA256 `e03de3f829e2b516c3ce6497878223b8b3722fd7cbda62d7651d1f01421f93f9`；不能声称该四臂完全证明正式区间无未预热警告。该结论仅覆盖所测请求与该生产运行。

### `P-BENCH-09`：冷暖进程之间覆盖测试脚本会制造输出差异 `[局部测试定位]`
- **现象与触发**：一次动态 `reshape/bmm` 冷暖测试均通过各自数值断言，但输出摘要不同。
- **真实根因**：冷进程启动后、暖进程启动前，测试脚本被更新，暖进程多执行了一次输入视图写入；两次实际测试输入因此不同，不能据此推断设备或 Recipe 缓存不确定。
- **硬性规避**：冷暖进程必须使用同一冻结测试脚本和输入；测试完成前不覆盖其运行文件，记录脚本及产物摘要。遇到摘要差异先核对输入和代码身份，不得跳过逐位比较。
- **证据落点**：不同脚本的失败记录 SHA256 `5fb6195e9d3caeb59562491d98af2e1a657eebf20dd7b35e5118ae742c9b3a82`；固定脚本后独立冷暖输出摘要一致的记录 `26a1cb48d5c80609e249a48e9a8ba7db61dd421cb4ef365b1cd5a618966a681e`。当次两版脚本的独立文件摘要未保存，故不能反推具体源码哈希。

### `P-BENCH-10`：设备序号与模块号不同，驱动显存读数可能按整卡显示 `[单卡分阶段验证]`
- **现象与触发**：一次单卡测试中，`module_id=0` 对应的 `hl-smi` 索引为 4；初始化 2 GiB 主池后，该卡 `memory.used` 从 768 MiB 显示为 98,304 MiB，写入 512 MiB 张量后不变，关闭运行时又回到 768 MiB。
- **真实根因**：设备枚举索引与 Synapse 模块号并非同一编号；在此环境中，初始化运行时和主池后驱动指标显示整卡占用，并不随已用池内字节变化。闭源驱动内部计账细节尚未核实。
- **硬性规避**：按 `module_id` 对应设备；分别报告一次申请的主池大小、分配器的峰值占用和 `hl-smi` 原始读数，不能把其他卡的空闲值或整卡显示值当成实际活跃张量峰值。
- **证据落点**：初始化、写入及关闭三阶段的单卡记录 SHA256 `43a02df6b4bb502953babfb228e267f2fba1e2bae48f4c9f6d6c6ba14272f0fd`。

### `P-BENCH-11`：逐步 KV 审计重复复制整池会掩盖验证成本 `[单卡与主机局部验证]`
- **现象与触发**：52 层逐步状态审计使用布尔索引分别检查历史和未触碰区时，每步都要多次扫描、复制整个 KV 池；这不是模型的无插桩延迟。
- **真实根因**：布尔索引为每层生成整池的临时副本，随后重复执行有限性、保持与零值扫描。
- **硬性规避**：从全零期望池出发，每步校验新写入有限并只更新目标槽位，然后与设备读回的整个池逐位比较；由前一步结果归纳验证历史不变及未触碰区域恒零。必须验证重复目标槽位、错误目标写入、历史污染、未触碰区污染和非有限值均被拒绝；冷暖使用同一冻结脚本，性能计时另开无逐步审计进程。
- **证据落点**：目标、历史、未触碰与非有限故障注入 SHA256 `34ab893f7c1aec24bd20de6732600058e7604777b7b13e99fee79e321e1d1617`，脚本落在 `sglang-gaudirt` `4fe00d2` 的 `tests/acceptance/`；目标几何两层与原审计的 logits 和 KV 轨迹逐字节一致，记录 `4788cd799578993351e02f6d841121eac90cd0311d343644005d5eb6de246d58`；52 层池大小的单次主机检查由 `1.032778 s` 降至 `0.062878 s`，记录 `01055d66156b6ff9b488b925797882ce1d61e4e191afbab519f1528bec45210b`。这不是模型性能对比。

### `P-BENCH-12`：最后一次前向的 Recipe 统计不等于进程退出时的总数 `[单卡冷暖全生命周期已验证]`
- **现象与触发**：真实 52 层冷验最后一次前向结束时记录 `60` 张常驻 Recipe，而进程正常退出后缓存目录有 `62` 张。
- **真实根因**：前向统计发生在请求后续处理完成之前；实测另有两张冷路径图在该统计之后、冷进程退出之前保存。两张图各自的上游调用位置尚未单独定位。
- **硬性规避**：区分最后一次前向的常驻数和进程退出后的磁盘总数；暖进程零重编译须覆盖整个进程生命周期，不能只检查最后一次模型前向。当前所有候选图编译经 `compile_cached` 且启用了磁盘缓存，可用冷进程退出时的文件集合与内容快照，结合暖进程退出时间检查是否新增 Recipe；任何新增或原有文件内容变化均应失败并排查。
- **证据落点**：真实冷验退出后 `62` 张的文件名与内容 SHA256 快照 `23e8c21e87da4cb8ed94551bc52c1b0c833ecb4b794fb7eec4b29f297362024a`，其中两张保存于最后一次前向统计之后；模拟新增暖图和修改冷图均被拒绝，检查记录 `bc68faa21b0698a3433e14b0427c76510f4ec45de0a8919e8117621ee2b8929a`。暖进程退出后的核对确认冷文件内容未变、暖期新增 `0` 张，收据 SHA256 `223ecae67ccb4637d8788954608172eb4d87e0414d5373908ecde4a56d92cddc`。分配器修复 `01db01f` 后重新验收仍为末次前向 `60` 张、冷退出 `62` 张、暖期新增 `0` 张，修复版核对收据 SHA256 `c822c0bceb7e99ae52abb08bbf05b159941607ada81bf1c5c1f1efac55c285da`。

### `P-BENCH-13`：短输出预热无法覆盖长输出的冷路径图 `[完整模型修复后单跑验证]`
- **现象与触发**：`1024` 输入、`128` 输出的计时只用 `2` 个输出预热时，计时前后累计编译数从 `10` 增至 `12`；测速脚本拒绝该次成绩，Worker 正常退出而主进程以 `1` 退出。
- **真实根因**：请求生成后段产生新的长度相关冷路径图；该次新增文件中后两张分别是长度 `1151` 的 INT32→INT64 转换与对应 `cat`，短预热没有覆盖它们。
- **硬性规避**：每个正式请求先以同样的输入长度和完整输出长度预热，再在计时前后检查编译计数相等；计时包含编译的运行不得记录为无插桩暖态成绩。
- **证据落点**：失败进程日志 SHA256 `9f6be1f9366178982875473785d32a07f45f19b1ba16109de8680fd20c405cc1`，新增 Recipe 的保存次序收据 `eef07fca475b748c711f850592e641f34c47cc8bb333a1d9e3dd2280efb3b5e3`；四个 Python 进程入口与退出隔离收据 `9500daaaa4eb5cf101939bf789da58386a7a84b627fae655f982fc806204e1f8`；插件测试脚本 `9e84412` 改为完整输出长度预热；两层目标几何的 `1024/4096` 输入、`128` 输出计时窗口均无新增编译，日志 SHA256 `73df6e87c08eae0125a6b25924111d4ba0bff2ab9ffed306f9ebdb9e72908737`。完整模型经完整长度预热后，`1024/4096` 的两个计时窗口均无新增编译，单跑收据 SHA256 `0557e69ed0700deb0d17b0540f762fb81423a176b1b1918b6ed7c851c95f8f80`。
